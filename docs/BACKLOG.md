## 1. งานค้างที่ต้องทำต่อ (เรียงตามความสำคัญ)

### 1.1 กรอกข้อมูลสินค้าเข้าโซน ⬅️ **บล็อกฟีเจอร์ใหม่ทั้งหมด**

หน้า **ผังโกดัง** (v1.5.0) สร้างเสร็จและใช้งานได้แล้ว แต่ **ยังไม่มีข้อมูลว่าสินค้าไหนอยู่โซนไหนเลย
(0 รายการ)** — ค้นหาไปก็ยังไม่เจออะไร

- ข้อมูลอยู่บน **กระดาษที่เจ้าของร้านเขียนไว้** เจ้าของบอกว่าถ่ายรูปมาแล้วแต่
  **รูปยังไม่ได้ถูกส่งเข้ามาในแชต** (ที่ส่งมามีแต่รูปผังโกดัง)
- **สิ่งที่ต้องขอ:** รูปกระดาษที่ระบุว่าโซน 1–13 แต่ละโซนมีสินค้าอะไร
- กรอกได้ 2 ทาง:
  1. **ในโปรแกรม** — หน้าผังโกดัง → กดโซน → เลือกสินค้า → "เพิ่มเข้าโซน" (ทีละรายการ)
  2. **ถ้ารายการเยอะ** — เขียนสคริปต์ insert เข้า `product_zones` ทีเดียว (เร็วกว่ามาก
     แต่ต้องปิดโปรแกรมก่อน เพราะ SQLite เป็น single-writer และ StockKeep ต้องเป็นผู้เขียนคนเดียว)

### 1.2 หน้าประวัติตรวจนับ — ทำใหม่ 3 ส่วน ⬅️ **ตกลงแนวทางแล้ว รอลงมือ**

เจ้าของสั่งไว้ชัดเจน (25 ส.ค. 69) ว่าเอา **แบบ ก.** สำหรับการแก้ไข:

1. **แสดงคลัง + หน้าร้านพร้อมกัน** — ตอนตรวจนับคีย์ทั้งสองที่พร้อมกัน แต่ตอนย้อนดู
   เห็นทีละอัน ต้องทำให้เห็นคู่กันเป็นตารางหน้าตาเหมือนตอนคีย์เข้าไป
2. **ออกเป็น PDF ตาม template** — ใช้เส้นทาง `printToPDF` ที่ทำไว้แล้วใน v1.4.3
3. **แก้ไขข้อมูลที่คีย์ผิดได้ — แบบ ก. (ออกรายการปรับใหม่)**
   กดแก้ในรอบเก่า → ระบบสร้าง **รอบใหม่ที่อ้างอิงรอบเดิม** แล้วลง `ADJUST` ตามส่วนต่าง
   **ห้าม UPDATE ตัวเลขในรอบเก่าทับ** เด็ดขาด
   > เหตุผลที่เลือกแบบนี้: โปรแกรมนี้ถูกสร้างมาแทน 4POS ที่แก้ยอดทับได้จนติดลบโดยไม่มีประวัติ
   > ถ้าเปิดให้แก้ทับ ปัญหาเดิมกลับมาทางประตูหลังทันที

### 1.3 หน้าตรวจนับ — กรอกแยกตามหน่วยได้ ⬅️ **สั่งแล้ว รอลงมือ**

ตอนนี้หน้าตรวจนับให้ **ช่องเดียวต่อคลัง** คนนับต้องคูณเอง เช่นมี 4 กล่อง (กล่องละ 24)
กับอีก 2 ชิ้น ต้องคิดเองเป็น 98 แล้วค่อยพิมพ์ — ผิดง่ายและช้า

- ต้องการ: **ช่องกรอกแยกตามระดับหน่วย** ต่อคลัง (ช่อง "กล่อง" กับช่อง "ชิ้น" แยกกัน)
  แล้วระบบคูณรวมเป็นหน่วยฐานให้เอง
- **การแสดงผลไม่ใช่ปัญหา** — `formatStock()` แยกหน่วยให้อยู่แล้ว ("4 กล่อง 2 ชิ้น")
  ปัญหาอยู่ที่ **ขาเข้า** อย่างเดียว
- ระวัง: `src/renderer/src/views/stocktake.ts` เป็นไฟล์ที่ใหญ่และเปราะที่สุด
  (ดีไซน์ 1a, กด Enter เลื่อนช่อง, แถบความคืบหน้า) — แก้แล้วต้องทดสอบการคีย์รัวด้วย

### 1.5 git ยังไม่มี commit แรก

`git init` แล้วเมื่อ 18 ส.ค. 2569 แต่ **repo ยังว่างเปล่า ไม่มี commit สักอัน** = ไม่มีจุดย้อนกลับเลย

```bash
cd "D:\Claude Code\Home\Program\stock-system" && git add . && git commit -m "StockKeep v1.5.0: warehouse zone map and product location search"
```

- `.gitignore` ครบแล้ว (กัน `node_modules/`, `out/`, `release/`, `dist/`, `*.log`)
- ไฟล์ที่จะถูกติดตามประมาณ 50 ไฟล์ ใหญ่สุดคือ `package-lock.json`
- **ตัวตนใน git:** ตั้งไว้ที่ระดับ repo (`git config --local`) ไม่ใช่ global
  เพื่อไม่ให้กระทบโปรเจกต์อื่นในเครื่องเดียวกัน
- ใช้ **noreply ของ GitHub** เป็นอีเมล commit — commit ยังผูกกับบัญชีและขึ้น contribution
  graph ตามปกติ แต่ไม่ฝังอีเมลจริงลงในประวัติแบบถาวร (repo ตั้งเป็น public)
- **ยังไม่มี remote** — โค้ดอยู่ในเครื่องอย่างเดียว

## 3. การตัดสินใจเชิงออกแบบที่ต้องรู้ (อย่าเปลี่ยนโดยไม่คิดให้ครบ)

### 3.1 โซนโกดังไม่ใช่มิติของสต๊อก

`zones` / `product_zones` เป็น **ตัวช่วยหาของเท่านั้น** ไม่ได้แตะ `stock_movements` เลย
ยอดคงเหลือยังนับตาม `locations` (คลังสินค้า / หน้าร้าน) เหมือนเดิม

**เหตุผล:** ถ้าทำโซนเป็นมิติของ ledger จะต้องระบุโซนทุกครั้งที่รับของ/เบิกของ/ตรวจนับ
ซึ่งเป็นการรื้อระบบสต๊อกทั้งระบบ และไม่ใช่สิ่งที่เจ้าของขอ (เจ้าของขอ "ตัวช่วยหาของ")

### 3.2 หน้าผังโกดังต้องไม่ส่งราคาผ่าน IPC

พนักงาน (level 1) ใช้หน้านี้ได้ ดังนั้น `src/main/ipc/zones.ts` ส่งเฉพาะ
`id / barcode / description / baseUnit / barcodePending` **ไม่มี cost หรือราคาทุกชั้น**
คงกติกาความปลอดภัยข้อ 1 ของโปรเจกต์ไว้ — **ถ้าจะเพิ่ม field ต้องระวังข้อนี้**

### 3.3 ผังเก็บเป็นข้อมูล ไม่ฝังในโค้ด

ตำแหน่งช่องอยู่ใน `zones.grid_col/grid_row/grid_w/grid_h` บนกริด **40 คอลัมน์**
(40 เพราะแถวบนแบ่ง 5 ช่อง แถวล่างแบ่ง 8 ช่อง — 40 คือความกว้างเล็กสุดที่ลงตัวทั้งคู่)
ปรับผังทีหลังได้โดยไม่ต้องแก้โปรแกรม

`kind` มี 3 แบบ: `zone` (เก็บของ กดได้) · `label` (ประตู/ออฟฟิศ) · `space` (ช่องว่างจัดรูปผัง)

### 3.4 ระยะขอบกระดาษและขนาดกระดาษเป็นค่า "ต่อเครื่อง"

เก็บใน `localStorage` ไม่ใช่ในฐานข้อมูล เพราะเป็นคุณสมบัติของ**เครื่องพิมพ์**ที่ต่อกับเครื่องนั้น
ไม่ใช่ของเอกสาร ถ้าฝังลงเลย์เอาต์ เครื่องที่กระดาษตรงอยู่แล้วจะเยื้องผิดทางแทน

คีย์ที่ใช้: `print.orderMargins`, `print.orderPaper`, `printer.orderTicket`, `printer.stocktake`

## 4. บทเรียนวิธีทำงานที่ควรจำ

### 4.1 เรื่องพิมพ์ — ห้ามเดา ให้วัด

ไล่บั๊กเรื่องพิมพ์ในรอบ v1.4.2–v1.4.3 **เดาผิดสามรอบ** ก่อนเจอต้นเหตุจริงทุกครั้ง
เครื่องมือที่ใช้ได้ผลคือ **`webContents.printToPDF()` เป็น oracle**:

```js
// สคริปต์ทิ้งขว้าง: โหลด out/renderer/index.html → ใส่แผ่นพิมพ์ → set body class
// → printToPDF → นับหน้า / อ่าน MediaBox / วัดระยะจาก getBoundingClientRect
```

ไม่ผ่าน driver ไม่ผ่านเครื่องพิมพ์ ผลคงที่ วัดได้จริง

**ห้ามใช้ `Microsoft Print to PDF` เป็นตัววัด** — silent print กับมันได้ไฟล์ **0 ไบต์**
และเคสเดียวกันให้ผลต่างกันคนละรอบ

### 4.2 ปิดโปรแกรมก่อน build เสมอ

- `npm run dist` ต้อง rebuild native module (`better-sqlite3`) ที่โปรแกรมล็อกไว้ → **EBUSY** ถ้าเปิดอยู่
- `npm start` ตอนที่โปรแกรมเปิดอยู่จะโดน **single-instance lock เตะทิ้งเงียบๆ (exit 0)**
  แล้วโฟกัสหน้าต่างเก่าแทน — **เคยทำให้ทดสอบโค้ดเก่าไปหนึ่งรอบเต็มโดยไม่รู้ตัว**
  → เช็ค process ก่อนเปิดทุกครั้ง

### 4.3 สภาพแวดล้อมของเครื่องนี้

- `node` **ไม่อยู่ใน PATH ของ Git Bash** → ต้องรัน `npm` ผ่าน **PowerShell**
- `better-sqlite3` ถูก build ไว้ให้ **Electron ABI** → รันด้วย `node` ธรรมดาจะ error
  `NODE_MODULE_VERSION` · **ห้าม `npm rebuild`** เพราะจะพัง Electron
  → อ่าน DB ด้วย: `$env:ELECTRON_RUN_AS_NODE="1"; .\node_modules\electron\dist\electron.exe script.js`
- PowerShell tool: cwd หลุดได้ → ใส่ `Set-Location` เต็ม path ทุกครั้ง
