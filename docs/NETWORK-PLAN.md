# แผนการทำระบบใช้ฐานข้อมูลร่วมกันผ่านเครือข่าย (Shared Database Plan)

> เอกสารนี้เป็น **แผน** สำหรับตัดสินใจร่วมกับลูกค้า — ยังไม่ได้เริ่มพัฒนา
> เวอร์ชันปัจจุบัน (v1.0.0) ยังเป็นแบบ standalone (แต่ละเครื่องมีฐานข้อมูลของตัวเอง) และยังใช้งานได้ตามปกติ
> วันที่จัดทำ: 22 กรกฎาคม 2569

## 1. เป้าหมาย

ให้คอมพิวเตอร์หลายเครื่องในร้านเห็น **ข้อมูลสต๊อกชุดเดียวกัน** แบบเรียลไทม์

**ขนาดที่วางแผนไว้:** เครื่องแม่ข่าย (main) 1 เครื่อง + เครื่องพนักงาน 4 เครื่อง = **รวม 5 เครื่อง**

| ตอนนี้ (v1.0.0) | เป้าหมาย |
|---|---|
| แต่ละเครื่องมีฐานข้อมูลแยกกัน | ฐานข้อมูลเดียว อยู่ที่เครื่องแม่ข่าย |
| ข้อมูลไม่ตรงกันระหว่างเครื่อง | ทุกเครื่องเห็นสต๊อกล่าสุดเหมือนกัน |
| ไม่ต้องต่อเน็ต/แลน | ต้องอยู่ในวง WiFi/LAN เดียวกัน |

## 2. ⚠️ สิ่งที่ห้ามทำ — แชร์ไฟล์ฐานข้อมูลผ่าน Shared Folder

วิธีที่คนมักคิดถึงก่อนคือ วางไฟล์ `stockkeep.db` ไว้ในโฟลเดอร์ที่แชร์ แล้วให้ทุกเครื่องเปิดไฟล์เดียวกัน

**วิธีนี้ทำให้ข้อมูลเสียหาย (corrupt) และห้ามใช้เด็ดขาด**

เหตุผล: SQLite ใช้กลไก file locking เพื่อกันไม่ให้สองคนเขียนพร้อมกัน แต่ Windows file sharing (SMB) ทำ locking ได้ไม่น่าเชื่อถือ ผลคือ **ใช้ได้ปกติเป็นสัปดาห์ แล้ววันหนึ่งมีคนบันทึกพร้อมกันสองคน ไฟล์พังทั้งไฟล์** — ทีมผู้พัฒนา SQLite เองเตือนเรื่องนี้ไว้ชัดเจน

**หลักการที่ถูกต้อง:** มีเครื่องเดียวที่เป็นเจ้าของไฟล์ฐานข้อมูล เครื่องอื่นต้อง "ขอข้อมูลผ่านเครื่องนั้น" ไม่ใช่เปิดไฟล์ตรงๆ

## 3. สถาปัตยกรรมที่แนะนำ

เครื่องแม่ข่ายเปิด **API server เล็กๆ อยู่ในตัวโปรแกรมเอง** เครื่องอื่นเชื่อมต่อเข้ามา

```
   เครื่องแม่ข่าย (MAIN PC)                เครื่องพนักงาน 4 เครื่อง
 ┌────────────────────────────┐        ┌────────────────────────┐
 │ StockKeep (โหมดแม่ข่าย)     │◄───────┤ StockKeep (โหมดลูกข่าย) │
 │  ├─ API server พอร์ต 3100   │        │  หน้าตาเหมือนเดิมทุกอย่าง│
 │  └─ SQLite (ไฟล์ฐานข้อมูล   │ WiFi   │  แต่ไม่มีฐานข้อมูลในเครื่อง│
 │     เดียวในระบบทั้งหมด)      │  หรือ  └────────────────────────┘
 └────────────────────────────┘  LAN   ┌────────────────────────┐
                                 ◄──────┤ StockKeep (โหมดลูกข่าย) │
                                        └────────────────────────┘
                                                 ... ฯลฯ
```

**จุดสำคัญ: เป็นโปรแกรมตัวเดียวกัน ใช้ installer ตัวเดียวกัน** ตอนติดตั้งครั้งแรกแค่เลือกว่าเครื่องนี้เป็น "แม่ข่าย" หรือ "ลูกข่าย" (ถ้าเป็นลูกข่ายก็กรอก IP ของเครื่องแม่ข่าย)

### ทำไมสถาปัตยกรรมนี้เหมาะกับโปรแกรมนี้เป็นพิเศษ

โค้ดปัจจุบันแยกส่วนไว้ดีอยู่แล้ว — business logic ทั้งหมดอยู่ใน `src/main/ipc/*.ts` และหน้าจอ (renderer) คุยผ่าน `window.api` เท่านั้น ไม่เคยแตะฐานข้อมูลโดยตรง

ดังนั้นการเปลี่ยนครั้งนี้ **แทบไม่ต้องแก้หน้าจอเลย** แค่เปลี่ยนว่าเบื้องหลัง `window.api` จะไปคุยกับอะไร:
- เครื่องแม่ข่าย → คุยกับ SQLite ในเครื่อง (เหมือนเดิม)
- เครื่องลูกข่าย → ส่ง HTTP ไปหาเครื่องแม่ข่าย

### ทำไมยังใช้ SQLite ไม่เปลี่ยนเป็น PostgreSQL/MySQL

สำหรับร้าน 5 เครื่อง ที่มีการบันทึกไม่กี่ครั้งต่อนาที **SQLite (โหมด WAL) เพียงพออย่างมาก** และคำขอทุกอันวิ่งผ่าน server process เดียว จึงไม่มีปัญหาแย่ง lock กัน

ถ้าเปลี่ยนไปใช้ PostgreSQL จะกลายเป็นว่าลูกค้าต้องติดตั้งและดูแลโปรแกรมฐานข้อมูลเพิ่มอีกตัว ซับซ้อนขึ้นโดยไม่จำเป็น

## 4. ความปลอดภัย — จุดที่เปลี่ยนไปอย่างสำคัญ

### 4.1 ขอบเขตความไว้ใจ (trust boundary) ย้ายที่

ปัจจุบันกฎ **"พนักงานห้ามเห็นต้นทุน / ราคาช่าง / ราคาส่ง"** ถูกบังคับที่ main process ของแต่ละเครื่อง ซึ่งปลอดภัยดี เพราะแต่ละเครื่องให้บริการเฉพาะคนที่นั่งอยู่หน้าเครื่องนั้น

**แต่พอมี API บนเครือข่าย** พนักงานที่รู้เรื่องคอมพิวเตอร์สามารถส่งคำขอตรงไปที่ server ได้เอง โดยไม่ผ่านหน้าจอโปรแกรม

**สิ่งที่ต้องทำ:** เครื่องแม่ข่ายต้อง **ตรวจสิทธิ์ใหม่ทุกคำขอ** และถือว่าเครื่องลูกข่ายเป็นฝ่ายที่เชื่อไม่ได้ (untrusted) — ข้อนี้บังคับ ไม่ใช่ทางเลือก มิฉะนั้นกฎการซ่อนราคาตามตำแหน่งจะใช้ไม่ได้จริง

### 4.2 มาตรการที่ต้องมี

| มาตรการ | ป้องกันอะไร |
|---|---|
| ทุกคำขอต้องแนบ token ของผู้ใช้ที่ล็อกอินแล้ว | คนที่ไม่ได้ล็อกอินเรียก API ไม่ได้ |
| server ตรวจ role ใหม่ทุกครั้ง ก่อนส่งข้อมูลราคา/ต้นทุน | พนักงานแอบดูราคาต้นทุน |
| Windows Firewall จำกัดให้เข้าถึงได้เฉพาะวงเครือข่ายภายใน | เครื่องนอกร้านเข้าถึงระบบ |
| server เปิดรับเฉพาะ network interface ของวง LAN | ลดพื้นที่เสี่ยง |
| แยก WiFi ลูกค้า (guest) ออกจาก WiFi ที่คอมใช้ | ลูกค้าที่รู้รหัส WiFi เข้าถึงระบบ |

### 4.3 ทางเลือกเพิ่มเติม: เข้ารหัส HTTPS

ถ้าต้องการความปลอดภัยสูงขึ้น สามารถเพิ่ม self-signed certificate เพื่อเข้ารหัสข้อมูลระหว่างเครื่อง (กันการดักฟังในวง WiFi) แต่ต้องติดตั้ง certificate ที่เครื่องลูกข่ายทุกเครื่อง เพิ่มขั้นตอนตอนติดตั้ง

**คำแนะนำ:** สำหรับร้านที่ใช้ WiFi ส่วนตัวมีรหัสผ่าน WPA2/WPA3 อยู่แล้ว (ซึ่งเข้ารหัสสัญญาณให้อยู่แล้วในระดับหนึ่ง) เริ่มจากแบบไม่มี HTTPS ก่อนได้ แล้วค่อยเพิ่มทีหลังถ้าลูกค้าต้องการ

## 5. WiFi หรือสายแลน — เลือกอย่างไร

**โค้ดโปรแกรมเหมือนกันทุกประการ** ต่างกันแค่การเดินสายจริง

| | WiFi | สายแลน (Ethernet) |
|---|---|---|
| โค้ดโปรแกรม | เหมือนกัน | เหมือนกัน |
| ความยุ่งยากตอนติดตั้ง | ง่าย ไม่ต้องเดินสาย | ต้องเดินสายทุกจุด |
| ความเสถียร | อาจหลุด/สัญญาณกวน | เสถียรมาก |
| ความปลอดภัย | ขึ้นกับความแข็งแรงของรหัส WiFi | เข้าถึงทางกายภาพยากกว่า |

**คำแนะนำ: ใช้ WiFi ได้เลย** ความเสี่ยงจริงไม่ได้อยู่ที่ตัวสัญญาณ (WPA2/WPA3 เข้ารหัสให้อยู่แล้ว) แต่อยู่ที่ 3 ข้อในหัวข้อ 4.2 ซึ่งแก้ได้ด้วยการตั้งค่าและโค้ด

**ยกเว้น:** ถ้าเครื่องแม่ข่ายอยู่ในจุดที่สัญญาณ WiFi อ่อน แนะนำให้ **เครื่องแม่ข่ายต่อสายแลน** (เพราะทุกเครื่องพึ่งพามัน) ส่วนเครื่องพนักงานใช้ WiFi ได้ — ผสมกันได้ ไม่มีปัญหา

## 7. ขอบเขตงานพัฒนา

| ไฟล์ / ส่วน | การเปลี่ยนแปลง |
|---|---|
| `src/renderer/**` | **ไม่ต้องแก้** ✅ |
| `src/main/ipc/*.ts` | ใช้ business logic เดิม ให้ทั้ง local และ server เรียกใช้ร่วมกัน |
| `src/main/session.ts` | จาก session ตัวเดียว → เก็บหลาย session แยกตาม token |
| `src/main/server.ts` | **ใหม่** — API server (ทำงานเฉพาะโหมดแม่ข่าย) |
| `src/main/client.ts` | **ใหม่** — ส่งคำขอผ่านเครือข่ายแทนการเปิด DB |
| หน้าตั้งค่า | **ใหม่** — เลือกโหมด + กรอก IP เครื่องแม่ข่าย |
| การแจ้งเตือน | **ใหม่** — แจ้งชัดเจนเมื่อเชื่อมต่อเครื่องแม่ข่ายไม่ได้ + ลองเชื่อมใหม่อัตโนมัติ |

### แบ่งเป็นเฟส

1. **เฟส 1** — แยกโค้ดให้ business logic ใช้ร่วมกันได้ + ระบบ token/session (ยังทำงานแบบ standalone เหมือนเดิม ยังไม่มีอะไรเปลี่ยนสำหรับผู้ใช้)
2. **เฟส 2** — สร้าง API server + client + หน้าตั้งค่าโหมด
3. **เฟส 3** — ทดสอบ 2 เครื่องจริง, จัดการกรณีเน็ตหลุด, ตั้ง firewall
4. **เฟส 4** — ระบบสำรองข้อมูลอัตโนมัติ + ทดสอบครบ 5 เครื่อง แล้วส่งมอบ

> หมายเหตุ: เฟส 1 เป็นการปรับโครงสร้างภายในล้วนๆ ทำได้โดยที่เวอร์ชันที่ลูกค้าใช้อยู่ไม่สะดุด

## 8. ความเสี่ยงและข้อจำกัดที่ต้องแจ้งลูกค้า

### 8.1 เครื่องแม่ข่ายกลายเป็นจุดเดียวที่พังทั้งระบบได้ (single point of failure)

ถ้าเครื่องแม่ข่ายปิด/เสีย/เน็ตหลุด → **เครื่องพนักงานทั้ง 4 เครื่องใช้งานไม่ได้เลย**

ระบบจะไม่มีโหมดออฟไลน์ เพราะการทำให้เครื่องลูกข่ายทำงานตอนไม่มีเน็ตแล้วค่อย sync ทีหลัง เป็นงานที่ใหญ่กว่ามาก (ต้องจัดการ conflict เมื่อสองเครื่องแก้ของชิ้นเดียวกัน) และมักไม่คุ้มสำหรับร้านที่เครื่องแม่ข่ายเปิดอยู่แล้วตลอด

**ถ้าลูกค้ารับข้อนี้ไม่ได้ ต้องคุยกันก่อนเริ่มพัฒนา** เพราะจะเปลี่ยนสถาปัตยกรรมทั้งหมด

### 8.2 การสำรองข้อมูลสำคัญขึ้นมาก

เดิมข้อมูลเสียหาย = เสียแค่เครื่องเดียว ตอนนี้ = **เสียข้อมูลทั้งร้าน**

แนะนำให้เพิ่มในโปรแกรม:
- ปุ่ม "สำรองข้อมูล" ในหน้าผู้ดูแลระบบ
- สำรองอัตโนมัติวันละครั้ง ไปยัง USB หรือโฟลเดอร์ Google Drive / OneDrive

### 8.3 ข้อดีที่ได้เพิ่มมา

- ประวัติ movement ledger จะสมบูรณ์จริง — เห็นได้ว่า **ใครทำอะไรจากเครื่องไหน** รวมทุกเครื่องในที่เดียว
- ไม่ต้องมานั่งรวมข้อมูลจากหลายเครื่องด้วยมือ

## 9. คำถามที่ต้องคุยกับลูกค้าก่อนเริ่ม

1. เครื่องแม่ข่ายจะเป็นเครื่องที่มีคนใช้งานด้วยหรือเป็นเครื่องเปิดทิ้งไว้เฉยๆ?
   (ถ้าเปิดทิ้งไว้เฉยๆ แนะนำให้เพิ่มฟีเจอร์ย่อลง system tray + เปิดอัตโนมัติตอนเปิดเครื่อง)
2. รับได้ไหมว่าถ้าเครื่องแม่ข่ายดับ ทุกเครื่องจะใช้งานไม่ได้? (ข้อ 8.1)
3. ต้องการ HTTPS เพิ่มหรือไม่? (ข้อ 4.3)
4. ต้องการให้สำรองข้อมูลอัตโนมัติไปที่ไหน — USB, Google Drive, หรือ OneDrive?
5. ในอนาคตจะมีสาขาที่สอง (คนละสถานที่) หรือไม่?
   **สำคัญ:** ถ้ามี แผนนี้จะใช้ไม่ได้ เพราะออกแบบมาสำหรับเครือข่ายภายในร้านเดียวเท่านั้น — การเชื่อมข้ามสาขาต้องใช้เซิร์ฟเวอร์บนอินเทอร์เน็ต ซึ่งเป็นคนละโจทย์และมีค่าใช้จ่ายรายเดือน
